## Top-3 Ranking

### 1. Sampling Forge (Dice Forge × Triage demand pacing) — 25/25

Crafting the faces of your own dice IS constructing a probability distribution; rolling IS sampling from it. There is zero gap between mechanic and statistical concept — the player literally manipulates the PMF, watches the sampling distribution emerge, and feels variance shrink. A demand card forces the player to USE each roll (it cannot become decoration). Decoration is structurally impossible: a die face is a parameter, not a cosmetic. Engine-building is genuine: an early investment in a tight, high-mean die unlocks higher-tier demands that compound into a stable of specialized dice.

**Board game:** *Dice Forge* (BGG 194594) — removable/upgradable die faces as core mechanic  
**Mobile game:** *Reigns* — each action immediately and visibly nudges persistent meters; instant cause→effect framing  
**UI source:** *Linear.app* — dense dark-UI with micro-interaction feedback on every state transition

### 2. Real-time triage (Coffee Rush pacing) — 20/25

Engine-building is weaker (mostly throughput optimization, not compounding state). A strong Candidate 2 if the Sampling Forge proves too complex for a v0 prototype.

**Board game:** *Coffee Rush* (BGG 377061) — real-time simultaneous action, decision density under pressure  
**Mobile game:** *Diner Dash* — escalating simultaneous demand management; player must prioritize under constraint

### 3. Pre-commit programming puzzle (Mechs vs Minions vibe) — 20/25

Direct fit for procedure topics (hypothesis-testing pipeline, regression diagnostics). Held back by rhythm: the thinking phase is bursty (intense planning, then passive watching), not a steady 15–30s cadence. Best suited as a secondary mode after the Sampling Forge is established.

**Board game:** *Mechs vs Minions* (BGG 209010) — program a sequence, watch execution, iterate

## #1 Detailed Spec — Sampling Forge

### One-sentence pitch

The player forges custom dice by buying and engraving faces (each face = an outcome with a value), then rolls them against demand cards — gradually learning that *the shape of the distribution you build determines the outcomes you get*.

### Core decision loop (every 15–30 seconds)

1. A **demand card** appears: e.g. "Deliver a mean ≈ 7 with low spread" or "Produce at least 10, but any roll over 12 spoils the batch."
2. Player has 2–3 dice with tappable faces. They spend earned tokens to **swap, add, or upgrade a face** (e.g. replace a `1`-face with a `6`-face, or split a face into two milder outcomes to cut variance). The **live mean marker** and **variance indicator** update instantly.
3. Player taps **Roll** — dice animate, result lands on an accumulating **sampling-distribution histogram**.
4. Outcome resolves against the demand; payout in tokens funds the next engraving. Repeat.

Every cycle = one engraving decision + one roll. Fits 15–30s comfortably.

### How the statistical concept is used

**Core topics:** Probability distributions · Expected value · Variance · Law of Large Numbers · Central Limit Theorem (later demands)

The die's face-set IS a probability mass function. Editing a face changes E[X] and Var(X) directly — the player sees the predicted mean move as they engrave. Rolling repeatedly builds an empirical histogram that converges toward the constructed PMF; the player *feels* the LLN. Later demands introduce summing two dice (CLT: sum trends bell-shaped) and conditional spoilage thresholds (tail risk, P(X > k)). The concept is never a label — it is the reason the die's face matters.

### Engine-building mechanic

Faces are permanent until re-engraved. Tokens compound. An early investment in a tight, high-mean die unlocks higher-tier demands that pay more tokens, which fund a *second* specialized die. The player builds a stable of dice: one low-variance "reliable" die, one high-ceiling "gambler" die. Mastery = the ability to tune the combined distribution on the fly. Sloppy early dice cap your demand tier — early correct intuition about variance snowballs into a dominant forge.

### Failure state (informative + recoverable)

A roll misses the demand (mean too high, or hit the spoilage tail). The histogram **highlights where the roll landed vs. the target band**, and a one-line Hebrew diagnostic appears:

> "התוצאה נפלה בזנב הימני — השונות שלך גבוהה מדי"  
> ("Result landed in the right tail — your variance is too high")

No life lost. Player keeps tokens, can re-engrave and re-roll. Failure teaches the exact parameter to fix.

### Session length

4–7 minutes per run on mobile (6–10 demand cards), one-handed, portrait. Daily-run friendly.

### Prototype scope (minimum viable for loop test)

**Zustand store `forgeStore.ts`:**
```typescript
interface Die { id: string; faces: number[] }
interface Demand {
  id: string
  type: 'mean' | 'tail' | 'sum'
  target: number
  band: number        // tolerance ± around target
  reward: number      // tokens on success
}
interface ForgeState {
  dice: Die[]
  tokens: number
  currentDemand: Demand | null
  rollHistory: number[]           // feeds histogram
  selectedDieId: string | null
  selectedFaceIdx: number | null
  engraveFace: (dieId: string, faceIdx: number, value: number) => void
  rollDice: () => void
  resolveDemand: (roll: number) => void
  drawDemand: () => void
}
```

**React components (all in `src/components/SamplingForge/`):**
- `<ForgeBench>` — dice tray with tappable faces; selected face glows gold
- `<FaceEditor>` — bottom sheet (mobile-first); swap/upgrade value; shows live E[X] and Var(X)
- `<RollButton>` — animated roll (spring animation); disabled during animation
- `<SamplingHistogram>` — SVG/Recharts bar chart; target band overlay + predicted-mean marker; accumulates across rolls
- `<DemandCard>` — Hebrew RTL demand text + reward badge
- `<DiagnosticBanner>` — Hebrew RTL feedback line on resolve; color-coded by hit/miss using `--teal` / `--red`

**Pure helper functions (src/utils/forgeStats.ts):**
- `mean(faces: number[]): number`
- `variance(faces: number[]): number`
- `sampleRoll(dice: Die[]): number`

**v0 scope:** Implement `'mean'` demand type only. That alone exercises the complete loop. No backend — pure client state.

**Feature flag:** `SAMPLING_FORGE` in `src/config/featureFlags.ts`
